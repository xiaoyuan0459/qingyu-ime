## 一、三档模型参数（用户提供的数字已核实正确）

来源：官方 HuggingFace 博客《PP-OCRv6: from 1.5M to 34.5M Parameters》与百度百科。**参数量 ≠ 存储体积**，两套数字都对但含义不同：

| 档位 | 参数量 | 存储体积 | 识别准确率 | 官方定位 |
| --- | --- | --- | --- | --- |
| Tiny | 1.5M | 4.4 MB | 73.5% | 边缘设备 /浏览器 |
| **Small** | **7.7M** | **20.4 MB**（实测下载 20.45） | 81.3% | **移动端** |
| Medium | 34.5M | 73.3 MB | 83.2% | 服务器 |

⚠️ 准确率口径：V6 指标来自**内部多场景评估集**，V5 来自通用评估集，**两套评估集不可横向比较**。81.3% 是**文本行识别**口径（一行全对才计分），不等于单字 top-1，与现有 HCCR 的 95.47% 不同量纲。

## 二、关键发现：V6 官方字表是 15,565 汉字（远超此前判断）

此前从 `ppocr_keys_v1.txt` 实测的 6270 字是**旧版字典**，不适用于 V6。
V6 的真实字表在 `inference.yml` 内嵌，实测：

- 条目总数 **18,708**，其中基本区汉字 **15,565**
- 覆盖 GB2312 全集（一级 3755 + 二级 3008）并大幅延伸至生僻字
- 末尾含 emoji 区（🚼🚽🚾🚿🛀🛁…）
- 位置 3750+ 已是「戊戋戌戍戎戏成我戒戔戕或戗战戙戚戛戞戟戠」等，确认远超一级字

对比现有 HCCR：**3755 → 15565 字，约 4.1倍**。

## 三、已自行转换（采用自产模型）

第三方成果经比对**未采用**，改为自行从官方 Apache-2.0 ONNX 转换，来源可追溯。

`tools/fetch-ppocr-model.py`：下载官方 ONNX → pnnx 转换 → fp16 量化 → 写入
`imesdk/src/main/assets/ppocrv6_rec/`，并校验 SHA-256 可复现。

| 产物 | 值 |
| --- | --- |
| `inference.ncnn.param` | 13,852 字节，158 层 |
| `inference.ncnn.bin` | 10,562,152 字节 = 10.07 MB |
| bin SHA-256 | `4f18228f0005d853100103f8116e8c2685ed6f2ecca6059a47396f569ee5581d` |
| `inference.yml` | 150,579 字节，官方原样（内嵌字表） |

**与第三方成果的对比结论：等价**。自产 bin 与 `sumeping` 的 bin **SHA-256 完全相同**
（`cmp` 逐字节通过），158 层结构与 7,767,517 权重数一致，19 种层类型分布零差异。
param 仅 16 字节差异，为浮点文本打印格式（`-3.402823e+38` vs `-3.40282347e38`、
`0.166667` vs `0.166666672`），不影响推理。故采用自产模型，理由是**来源与许可清晰**
（官方 apache-2.0），而非质量更优 —— 两者完全相同。

## 四、识别链路已实测通过

`tools/verify-ppocr-model.py`：用 onnxruntime 跑官方 ONNX，对渲染汉字图做 CTC 解码。
渲染测试字（一级 / GB2312 二级 / 生僻）6/6 识别正确：

| 字 | 类别 | 置信度 |
| --- | --- | --- |
| 中 | 一级常用 | 1.000 |
| 国 | 一级常用 | 1.000 |
| 驸 | GB2312 二级 | 0.575 |
| 醍 | GB2312 二级 | 1.000 |
| 鑫 | 生僻字 | 1.000 |
| 龘 | 生僻字（3 龙） | 0.418（误识为「蒙影」，印刷体极复杂字的已知弱项） |

### CTC 通道布局（实测确认，勿按常见假设改）

输出维度 = 字表 18,708 + blank + 1 个保留通道 = **18,710**，布局为：

```
id 0            = blank（空白帧 argmax 落在此处，实测确认）
id 1..18708     = 字表第 0..18707 项，整体后移1 位
id 18709        = 保留通道
```

⚠️ **blank 是首通道，不是末尾**。按"末尾为 blank"的常见写法会解出首尾多余的 `!`
（字表首项是 `!`）。此结论已写入 `verify-ppocr-model.py` 的注释与实现。

## 五、与现有实现的差异（实现推理层时注意）

现有：`HWEngine.renderStrokesToGray()` 把笔画渲染为灰度图 → `hccr_jni.cc`（116 行，ncnn 直调）
→ `HCCRRecognizer.java` → `HWEngine`。

换V6 需要注意的差异：

1. **任务形态**：V6 是文本行识别（CTC/SVTR + 18710 分类头），现有是单字 3755 类分类。CTC 需处理blank 与重复字折叠，单字场景不能按整行解码逻辑直接套。
2. **输入尺寸**：V6 rec 是可变宽高比输入（文本行），单字需传方形且保持长宽比；现有预处理是 360 目标长边 + 笔宽 4.4% + 关 AA + lineTo。
3. **字表规模**：输出维度 18710 对应 18706 字表 + 4 特殊 token，映射表需按官方 yml顺序生成，不可自行排序。
4. **推理层**：现有 `nativeInit/nativePredict/nativeRelease/nativePreprocess` 四方法接口可沿用，但需重写 ncnn 层加载与后处理。
5. **体积**：4.1 MB → 10.07 MB（INT8 ncnn），比官方 FP32 的 20.4 MB 小一半。

## 六、待验证项（官方无数据，必须实测）

- 官方**未公布手写中文专项准确率**，也未公布 V6 手写场景指标
- 官方未公布单字场景准确率；81.3% 是文本行口径
- 单字手写（含连笔、简笔、笔画顺序自由）与文本行训练分布的差距未知
- 推理延迟未实测（现有 2–5 ms，V6 模型更大需重新测）
- 低频字（3755 之外的字）准确率可能显著下降；实测「龘」这类复杂字误识为「蒙影」

**已完成的实测**：印刷体渲染单字 6/6 正确（见第四节）。仍需用手写真实笔迹复测，
印刷体结果不能替代手写场景结论。

**建议验证顺序**：先用 `tools/verify-ppocr-model.py` 接自己的手写灰度图批量测 top-1 与耗时，
再决定是否替换 `hccr_jni.cc`。
