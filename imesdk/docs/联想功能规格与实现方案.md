# 联想（中文联想）功能规格与实现方案

**状态**：行为规格已确认（产品负责人 2026-09-19 口述）；实现排在 native 层的 P3。
**背景**：联想是本工程**唯一需要自研**的 librime 私有能力 —— 旧 `libyuyanime.so` 把
`rime::AssociateRear` 等 58 个符号编进了 librime 本体，上游 `rime_api.h` 完全没有对应 API。

---

## 一、行为规格（已确认）

1. **触发时机**：中文模式下**上屏后**（光标位置变化时触发），取光标前最多 10 个字符作为联想键。
2. **基本行为**：以刚输入的**字/词为前缀**列出后续词。
   例：输入「原」→ 候选栏出现「原来」「原神」。
3. **习惯学习**：随用户选词习惯累积，联想结果**逐渐偏向用户用过的后续词**。
4. **标点联动**：联想候选中夹带标点提示（`，` `。` `！` `？`）。
   **默认关闭**，设置中可开启。**不做日期联想** —— 原先「今天/明天/昨天…」结尾注入日期的行为已移除。
5. **总开关**：用户可整体关闭联想。

## 四、✅ 已修：`selectAssociation` 的索引错位

```kotlin
// RimeEngine.kt:116-121
fun selectAssociation(index: Int) {
    val indexReal = index - customPhraseSize
    Rime.chooseAssociate(indexReal)
    updateCandidatesOrCommitText()
    preCommitText = showCandidates.getOrNull(indexReal)?.text ?: ""
}
```

`customPhraseSize`（`RimeEngine.kt:25` 定义，`:184` 重置，`:193` 赋值）是**普通候选列表**
前面追加的自定义短语数量，由 `updateCandidatesOrCommitText` 维护。

问题：联想列表的结构是 `native[0..4] + 标点 + native[5..]`，与自定义短语毫无关系，
且 `predictAssociationWords` **不会重置** `customPhraseSize`。

→ 若上一次候选更新留下了非 0 的 `customPhraseSize`，`indexReal` 就会整体错位：
点标点项可能提交成 native 联想词，点 native 第 6 个起的项会偏移。
另外 `preCommitText` 又拿 `indexReal` 去索引 `showCandidates`，把两个索引空间混用了。

### 修法（2026-09-19）

`predictAssociationWords` 在构建显示列表的同时记录一份**「显示位置 → native 索引」映射**
（`associateIndexMap`，`-1` 表示非 native 项），`selectAssociation` 据此取值：

```kotlin
fun selectAssociation(index: Int) {
    val selected = showCandidates.getOrNull(index)   // 先取出用户点的那一项
    val nativeIndex = associateIndexMap.getOrNull(index) ?: -1
    if (nativeIndex >= 0) Rime.chooseAssociate(nativeIndex)  // 只有 native 词才回调引擎
    updateCandidatesOrCommitText()
    preCommitText = selected?.text ?: ""
}
```

一次修掉三个问题：

1. 不再复用属于**普通候选空间**的 `customPhraseSize`；
2. `getAssociateList` 返回 `Array<String?>`，null 被过滤造成的显示位移被映射吸收；
3. 标点联动开关导致的列表长度变化不再错位，且标点项**不再**误回调 `chooseAssociate`。

另外 `selected` 在 `updateCandidatesOrCommitText()` **之前**取出，避免列表被重建后取空。

> ⚠️ 这是**行为性修改**，本机无法运行 IME —— **必须真机验证**联想选中与标点上屏。

## 六、我们的实现方案（不 fork librime）

- 自研 gear 放在本仓库**独立源目录**，编译成静态库链进 `libqingyu_rime.so`，
  用 `RIME_REGISTER_MODULE` 注册 → **librime 保持 pristine，升级只换 tag**
- 可用的上游原语（已在 `rime/librime` master 的 `src/rime/dict/dictionary.h` 实测）：
  - `size_t Dictionary::LookupWords(DictEntryIterator*, const string& str_code, bool predictive, size_t limit, ...)`
    —— 注释原文：*if predictive is true, do an expand search with limit*
  - `an<DictEntryCollector> Dictionary::Lookup(const SyllableGraph&, ..., bool predict_word, ...)`
  - `Dictionary` 标记 `RIME_DLL` → 外部 gear 可直接调用
- JNI 暴露**自有 C API**（`qingyu_associate_*`），不沿用旧补丁的 `rime_associate_*` 命名

## 八、多字联想键的取法（建议，待确认）

问题：联想键是「光标前最多 10 字符」（`InputView.kt:763`）。单字场景没有歧义，
但多字（如已上屏「原来」）时，「整串前缀」与「只看末字」会得到完全不同的结果。

**建议：不要二选一，按「前缀补全」与「习惯后续」拆成两条路径。**

| 路径 | 键 | 操作 | 示例 |
|---|---|---|---|
| 冷启动（无习惯数据） | **末尾 1 个字** | 默认词表**前缀补全** | 「原」→ 原来、原神 |
| 热路径（有习惯数据） | **光标前最多 10 字符的上下文** | 匹配用户在同一/相似上下文之后常输入的词（**后续**） | 「原来」→ 如此 |

排序：热路径命中优先，其后接冷启动的前缀补全结果。

### 为什么这样拆

1. **你描述的行为本身就是两种**：「打原字出原来/原神」是前缀补全；
   「有选词习惯后出现用词习惯的后续」是后续预测。两者键不同，不该共用一个键。
2. **整串前缀在多字时会迅速退化为空** —— 以「原来」为前缀，词典里几乎没有以「原来」开头的词；
   而 10 字符键若当前缀用，基本必然为空。
   反过来看，**10 字符这个长度只有在「上下文匹配」语义下才有意义**，
   这本身就是原设计意图的旁证。
3. **末字前缀能保证任何状态下都有候选可出**，体验不会突然空掉。

### 分阶段

- **v1（随 native 自研一起做）**：只做冷启动路径（末字 + 默认词表前缀补全），
  已足以复现你描述的可见行为。
- **v2（v1 之后）**：加上 10 字符上下文的习惯后续。需先确认习惯数据落点
  （librime userdb 还是独立习惯表，见第七节风险 3）。

### 对实现的影响

若采纳，`FilterPrefixForList` 的比较对象是**末字**而非整串；
10 字符键只用于习惯路径的上下文匹配。与旧实现的符号命名
（`LeftAssociateCompare`、`FilterPrefixForList`）不冲突。

## 九、实际落地（2026-09-19）—— 本文第六、七节的前提被实测推翻

### 第六节的方案不成立

「用 `Dictionary::LookupWords(str_code, predictive=true)` 做文字前缀补全」不成立：
该接口的 `str_code` 走 prism，是**拼音码**不是文字（见 `dict/dictionary.cc` 实现首行
`prism_->ExpandSearch(str_code, …)`）。按文字前缀查需要 `*.reverse.bin`，
第七节风险 1 由此从「待验证」升级为**确证阻塞**。

### 新发现的可用原语：补半个后续音节

实测（AVD `qingyu_test`，`EngineSelfCheckActivity` ⑥）：

| 送入引擎的输入 | 候选总数 | 带 `~` 的预测项 | 以「原」开头的多字词 |
|---|---|---|---|
| `yuan` | 828 | 0 | **0** |
| `yuanl` | 867 | 0 | **7**：原来 原理 原料 原谅 原路 原粮 原鹿 |
| `yuanh` | 865 | 0 | 3：原话 原画 原核 |

即：**只送整音节时词库的同音节层里只有单字**；补上一个「半个后续音节」后
`script_translator` 的 completion 才会带出多字词。一个字母覆盖不了所有声母，
故按 26 个字母各探测一次再合并。

### 落地形态（librime 保持 pristine）

- `assets/rime/build/associate.schema.yaml`：内部方案，`script_translator` +
  `translator/enable_completion: true` + `menu/page_size: 1000`，
  复用全拼的 `pinyin.table.bin` / `pinyin.prism.bin`。
  **不进 `default.yaml` 的 schema_list**，用户不可选。
- `com.qingyu.inputmethod.AssociatePredictor`：末字 → 无调拼音（`HanziPinyin`，
  ü 归一为 `v`）→ 26 次前缀探测 → 名次轮转合并 → `LruCache`；
  习惯学习用 SharedPreferences 存每个末字的最近选词 MRU。
  查询期间临时 `selectSchema("associate")`，切回后重设 `traditionalization` / `emoji`。
- 上屏语义：候选显示**完整词**（「原来」），提交时去掉已上屏的前缀那个字
  （`RimeEngine.selectAssociation` 里 `removePrefix`）。

**没有新增任何 JNI 符号**，第八节设想的 v1/v2 两条路径合成了一条：
词典前缀补全 + 用户 MRU 排序。`jni.cc` 的 `nativeAssociateWords` /
`nativeSelectAssociate` 两个桩自此无人调用，待清理。

### 实测结果与遗留局限

`words("原")` = 30 项；首次 269 ms（26 次探测），缓存命中 0 ms；选过「原神」后排到首位。

1. 拼音取 `pinyin_table.txt` 的**第一读音**，多音字按第一读音查不到时该字无联想。
2. 无全局词频可用，只能按各次探测内的名次合并，会混入词库里的生僻组合（实测有「原哦」）。
3. 269 ms 落在 IME 主线程上，首次触发某末字时可感卡顿。

## 十、迁移原则（2026-09-19 确立）

> **按语义命名，不按位置命名；迁移过程同时是重构，不是原样照搬。**

本次「中文联想显示时间」事故就是反例：三个联想设置项在 `AppPrefs.kt` **相邻定义**、
UI 中**相邻**，命名便顺手复用了 `chinese_association_*` 前缀 —— 结果一个控制
「常用语 + 日期时间」的开关被安上了与自身功能无关的名字，还连带写错了说明文案。

具体落到本工程：

- 一个设置项的 **key、文案、Kotlin 字段**，三者都要能独立说清自己的职责；
  出现「名字解释不了行为」时，就地改名，不要留着。
- 迁移中遇到名不副实的旧标识（符号名、常量、方法名），**按语义重命名**，
  而不是为了"少改一处"原样搬过来。
- 本工程 applicationId 全新、**无已发布安装** → 改持久化 key 没有迁移成本，
  **现在改最便宜**；一旦发布再改就要写兼容解码（参考旧工程 `SkbStyleMode` 的"改名地雷"）。
- **P1 具体待办**：写自研 JNI 时，16 个 native 方法不必照搬旧的 `Rime` 前缀直译名
  （如 `processRimeKey`、`getRimeKeycodeByName`、`replaceRimeKey`）——
  Kotlin 侧与 C 侧都由我们自己定义，可以一并按语义命名。
