## 三、本轮改动

### 1. 中文联想（唯一需要自研的能力）

行为规格不变（上屏后取光标前文本、以**末字**为前缀列后续词、随选词习惯排序、
标点联动默认关闭）。实现路径与规格文档原设想**不同**，原因是实测推翻了它的前提：

- 上游 `Dictionary::LookupWords(str_code, predictive=true)` 的键是**拼音**（走 prism），
  不是文字；按文字前缀查需要 `*.reverse.bin`，而 `assets/rime/build/` 里没有它。
- 只送整音节 `yuan` 时，实测 828 项候选**全是单字**、0 项带 `~` 预测标记 ——
  词库的同音节层里只有码长恰为该音节的词条。
- **补上「半个后续音节」后 completion 才生效**：送 `yuanl` 立刻得到
  原来 / 原理 / 原料 / 原谅 / 原路。因此按 26 个声母字母各查一次再合并。

落地为两处，**librime 保持 pristine、不 fork、不加 JNI 符号**：

- `assets/rime/build/associate.schema.yaml`：内部方案，`script_translator` +
  `translator/enable_completion` + `menu/page_size: 1000`，复用全拼的
  `pinyin.table.bin` / `pinyin.prism.bin`（不触发第二次词典装载）。不进 `default.yaml`
  的 `schema_list`，用户不可选。
- `com.qingyu.inputmethod.AssociatePredictor`：末字 → 无调拼音（`HanziPinyin`，
  ü 归一为 `v`）→ 26 次前缀探测 → 名次轮转合并 → 进程内 `LruCache`；
  习惯学习用 SharedPreferences 存每个末字的最近选词 MRU，命中即排到首位。
  查询期间临时切方案，切回后重设 `traditionalization` / `emoji` 选项。

实测：`words("原")` = 30 项（原本、原创、原地、原封、原话、原价、原矿、原来、原名…），
**首次 252 ms（同型多次实测落在 225–401 ms）、缓存命中 0 ms**；选过一次该词后排到首位。

已知局限（写清楚，不当成已完成）：
- 拼音取 `pinyin_table.txt` 的**第一读音**，多音字（长、好、行…）按第一读音查不到时该字无联想。
- 首字候选里会混入词库中的生僻组合（实测出现「原哦」），无全局词频可用，只能按各探测内名次合并。
- 首次检索 250–400 ms 量级落在 IME 主线程上，首次触发某末字时会有可感卡顿；缓存后无感。

### 2. 候选页大小

`setRimePageSize(100)` 是旧私有补丁的能力，上游没有。改为把
`menu/page_size: 100` 写进 11 个 schema + `default.yaml`，恢复上游「一页 100 候选」的体验。
`associate` 方案单独用 1000，只为一次读全、少翻页。

### 3. 自检harness 扩容

`app/src/debug/.../EngineSelfCheckActivity.kt` 从 6 段扩到 10 段，把 MIGRATION 里
长期挂「未验证」的项变成有断言的检查：翻页、英文方案、九宫格方案、联想（含前缀正确性
与习惯学习两条断言）、以及冷/热耗时。

### 4. 中英混输 / 五笔画 / 乱序17（本轮补齐的三项）

**中英混输**：原先记为「数据缺口」的判断是错的 —— `tools/build-rime-pack.py` 一直在把 rime-ice 的
`en_dicts/` 拷进部署输入。真正的机制是：`cn_en` 段用 `db_class: stabledb`，而 librime 的
`DbComponent<StableDb>::extension()` 就是 `.txt`（`dict/table_db.cc`），即**它把文本表直接当只读库**，
不编译、不产出 `.table.bin`；解析根是「用户目录 → shared 目录」回退（`service.cc`
`CreateResourceResolver`），而 pack 目录恰好就是 `shared_data_dir`，所以 `.txt` 随包分发即可被读到。
按方案各用自己的分表接回 7 份 schema（`pinyin` + 6 个双拼）。**九宫格与乱序17 没接**：它们送进引擎的
是键码而非拼音码，`Xguang` 这类码到不了。当年那个「cn_en 会让会话创建 SIGSEGV」的结论也一并作废：
接上后 14 段自检全绿、无崩溃，崩溃应是 M3 之前那份被改过头部的二进制引起的。

**五笔画**：词库取 rime 官方仓 `rime/rime-stroke` @ `1e8fff9b`（LGPL-3.0-or-later；主码表源自台湾
CNS11643 全字库、附码表源自北大中文论坛，归属随 `AUTHORS.rime-stroke` 打进 pack）。上游码是小写
`hspnz`，而本应用的笔画键盘送大写码（`InputView` 给该键盘带 `META_CAPS_LOCK_ON`），故 schema 里
用 5 条 `xform` 整体翻成大写 —— 用 `derive` 会让每个码产生 2^码长 个大小写变体，棱镜直接炸。
产物 `stroke.prism.bin` 7.3 MB + `stroke.table.bin` 4.5 MB（旧继承版那个 41 MB 的棱镜没有再来）。
笔画键盘上第 6 个键是「通配」，librime 没有通配能力，**该键当前无效果**，待决。

**乱序17**：键表一直在 `LX17PinYinUtils.kt`（17 声母键 × 17 韵母键 → 音节，枚举而非可组合规则），
但棱镜里一条二码规则都没有，所以这个方案从来打不出字。新增 `tools/gen-ls17-algebra.py`，
以那张键表为单一事实来源生成 415 条 `derive`，棱镜从 22 KB 长到 33 KB。自检 ⑪ 做的是闭环校验：
用键表拼出键码 → 送进引擎 → 候选里必须有一个字的读音正是那个音节。

### 5. 顺带抓到并修掉的静默回归：共用棱镜互相覆盖

部署器按 `default.yaml` 的 `schema_list` 顺序编译，**同名棱镜后写的覆盖先写的**。`associate`
复用 `prism: pinyin` 却没带 `speller/algebra`，而它排在全拼之后 —— 于是 `pinyin.prism.bin`
被一份「无拼写规则」的版本覆盖，**超级简拼（单字母）整份消失**（`b`/`c`/… 全部 miss），
pack 里那份 4.4 KB 的棱镜就是证据（正常 22.5 KB）。M3 留下的码空间基线把这次回归照了出来。
修法：`associate` 带上与全拼逐条一致的 algebra；`tools/build-rime-pack.py` 新增
`assert_shared_prisms_agree()` 在组装阶段设卡（共用棱镜时，最后编译的那份必须是该词典自己的方案，
否则要求各方规则一致）。复验：pinyin / t9 / 6 个双拼共 34.5 万个探测码，与 M3 基线**零差异**。

7. **`english.prism.bin` 由 9 份方案共用**（中文方案里的 `table_translator@english`）—— 现依赖
   `english` 方案在 `schema_list` 里排最后来定稿；组装阶段已有卡口，但这是个需要记住的耦合。

### 6. 白霜 pack（独立分发，不进 APK）

`tools/build-rime-pack.py` 加了 `--upstream {ice,frost}`：两套上游各自固定 revision，
共用同一份自写装配清单（`imesdk/rime-src/*.dict.yaml`）与同一套方案/棱镜规则 —— 方案 id 不变
（`pinyin` / `t9_pinyin` / `double_pinyin_*` / `stroke` / `english`），所以换包之后 UI 与键表都不用动。
白霜仓里的分表名与雾凇一致（`cn_dicts/{8105,41448,base,ext,tencent,others}`、`en_dicts/*`、
7 份 `cn_en*.txt`），因此清单零改动。

产物：`build/rime-pack/rime-frost-qingyu-2026.09.20+96278d8.zip`（22.5 MB，48 文件，解包 52.8 MB），
`id=rime-frost-qingyu`、SPDX `GPL-3.0-or-later`（白霜仓内只有 GPL-3.0 正文、README 未声明 only，
故按 SPDX 惯例记 or-later；雾凇仓明确写 only，记 `GPL-3.0-only`）。
脚本对非默认上游设了硬卡：`--archive-out` 落在 `assets/` 下直接退出 —— 白霜只能独立分发。

实测（自检 ⑮，走的是设置页同一条 `RimePackManager.install`）：
`当前 pack = rime-ice-qingyu` → 导入白霜 → `已启用 白霜拼音（轻语版）2026.09.20+96278d8` →
新词库下 `nihao` 出候选 → `rollback()` 回到 `rime-ice-qingyu` 且照常打字。
候选深度不是换包就变差：`qingyu_probe --entries` 实测每音节词条数 shi 416（雾凇 374）、
ni 199（173）、hua 143（128）；`pinyin.table.bin` 两份哈希不同（38.8 MB / 70.5 MB），
确认编译确实吃了白霜的分表而不是静默回落到雾凇。
